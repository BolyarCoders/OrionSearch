# PostgreSQL persistence

## Native Identity extension (2026-10-28)

The original ORION-10/12 foundation below has eight migrations and fifteen tables.
The ninth migration, `20261028193247_AddNativeIdentity`, preserves these tables and
existing user IDs while extending `auth.users` for ASP.NET Core Identity and
adding `system.data_protection_keys` (sixteen tables excluding EF history).
See [Native Identity](native-identity.md) for schema ownership, activation,
backwards compatibility, token-key backup and rollback constraints. The original
eight migrations are unchanged. Legacy accounts remain unconfirmed and receive
no fabricated credentials or external identity links.

Normalized email has a unique index for Identity lookup. Existing `citext` email
uniqueness remains the backstop for legacy and concurrent mixed-case signups.
Concurrency stamps prevent stale Identity writes from overwriting a newer
account state; security stamps revoke previously issued sessions. These are
authoritative account fields, not derived caches. The nonnegative failed-access
count is constrained in PostgreSQL. Data Protection XML is private key material,
encrypted by certificate outside Development and never exposed through the API.

## Capture access grants (P3)

`20261028220005_ScopeCapturedVersionsToArchives` adds
content.archive_document_versions after the nine existing migrations. It binds
archive/document/version through composite foreign keys and stores the raw
URI/digest accepted by that archive, separately from globally deduplicated text.
Backfill grants only evidence-proven text versions; historical raw locators are
not made downloadable. Fresh/upgrade/idempotence and mismatch constraints are
covered by PostgreSQL tests. Downgrade refuses to discard populated access
grants. See [capture storage](capture-storage.md) for byte verification, ownership,
authorization, indices and conservative orphan retention. No hosted migration is
applied automatically by API startup.

## Original foundation

ORION-10 implements the 15-table MVP. The broader version-1.0 database specification was not present in the repository; the task's explicit table and integrity requirements are the implementation target.

## Tables and ownership

| Schema | Tables | Authoritative data |
| --- | --- | --- |
| `auth` | `users`, `archive_members` | User records and archive membership roles |
| `research` | `archives`, `archive_settings`, `research_runs`, `research_queries` | Archive configuration and logical research history |
| `content` | `publishers`, `documents`, `document_versions`, `archive_documents`, `document_chunks` | Source identity, captured content versions, archive associations and addressable excerpts |
| `knowledge` | `findings`, `finding_evidence` | Statements and their provenance links to captured versions |
| `system` | `jobs`, `job_attempts` | Executable work state and attempt history |
| `ai`, `publishing` | None | Reserved for later phases |

EF's migration-history table also lives in `system`; it is not a product table. There are no embedding, magazine or archive-finding tables.

The backend is the persistence writer. Research ingestion and the independent Python worker cross explicit application/JSON contracts rather than becoming a second schema owner. Source material and provenance are retained; chunks, hashes, model confidence, relevance scores and run statistics are derived from source content or processing. A derived value's producer must remain attributable to its version/run rather than being mistaken for ground truth.

## Integrity rules

- Independent entities have UUID primary keys generated by PostgreSQL's `gen_random_uuid()`. Junctions use the specified composite keys; settings use their archive ID as both PK and FK.
- Emails use `citext` with a unique index. Password hashes remain nullable; no authentication provider or hashing scheme is selected.
- Every foreign key is explicitly mapped. Archives reference an existing owner. Membership roles are constrained, `(archive_id, user_id)` is unique, and a partial unique index permits at most one owner membership per archive.
- That partial index **cannot require an owner membership to exist or match `archives.owner_id`**. ArchiveService creates the archive, matching owner membership and settings atomically, and checks persisted ownership consistency before authorized operations.
- Settings have a one-to-one archive FK. Date boundaries use `date` and may be omitted; when both exist, `date_from <= date_to`. Arrays default to empty `text[]` and config to an empty JSONB object.
- States, roles, trigger types, finding types, evidence stances and the specified job types have database CHECK constraints. These constrain stored values; they do not implement a workflow state machine.
- Documents are global, with a unique canonical URL. An archive links to a document via `archive_documents`; deleting an archive association does not delete the global source. Publisher domains are normalized and unique.
- Versions are unique by `(document_id, content_hash)`. Hashes remain required and must be 64 lowercase hexadecimal characters. Text and raw-byte hashing policies are described below; PostgreSQL validates hash format, uniqueness and raw-only provenance metadata, not the digest against externally stored bytes.
- Publication dates stay nullable. `published_at`, `first_seen_at`/`last_seen_at`, and version `fetched_at` describe different events; no publication date is inferred from fetching.
- Chunk indexes are nonnegative and unique within a version. Token counts may be absent, otherwise nonnegative. Offsets are either both absent or a nonnegative start and strictly greater end; the provisional research boundary uses Unicode scalar offsets in normalized extracted text, start inclusive/end exclusive, and checks the exact substring.
- Evidence always references an existing finding and document version. A supporting unique key on chunks `(id, version_id)` and the composite FK `(chunk_id, document_version_id)` prevent attaching another version's chunk. A null chunk is allowed while the separate document-version FK remains enforced.
- Relevance and confidence are nullable numeric values in `[0, 1]`. Model-generated confidence is metadata, not a calibrated probability of truth.
- Job attempts satisfy `0 <= attempts <= max_attempts` and `max_attempts > 0`. Attempt numbers start at one and are unique per job. Non-null idempotency keys are unique; multiple null keys are allowed. EF sends explicit attempt limits, including zero, so invalid values cannot silently turn into the database default of three.
- JSON fields are opaque strings mapped to JSONB objects. PostgreSQL validates JSON and object roots. Research job payloads use the explicitly provisional versioned contract; public status maps only known fields.

All timestamps use `timestamptz` and .NET UTC `DateTime`. Created/discovery/fetch defaults use the transaction time, `now()`. A shared BEFORE UPDATE trigger sets `updated_at` to `statement_timestamp()` on users, archives, settings, documents and jobs, including writes outside EF. Callers must supply UTC for explicit timestamps; Npgsql rejects non-UTC values.

`homepage_url` is optional. A document version may have null `extracted_text` if it has a durable `storage_uri` for captured raw content. `ck_document_versions_content_presence` enforces `extracted_text IS NOT NULL OR storage_uri IS NOT NULL`. A discovered URL with no captured representation belongs in `content.documents`; it does not justify a version row.

## Captured representations and hashes

For successfully extracted text, `ContentFingerprint.Compute(text)` retains the original policy: NFC Unicode normalization, LF line endings, trimming outer whitespace, UTF-8 encoding, then SHA-256. Internal whitespace is preserved. New ingestion should record `metadata.content_hash.algorithm = "sha256"` and `metadata.content_hash.basis = "normalized_extracted_text"`, with `normalization = "nfc_lf_trim_v1"` alongside them. Legacy extracted-text rows with `{}` metadata remain valid and are not backfilled with assumed provenance.

For raw-only captures, use `ContentFingerprint.ComputeRaw(bytes)` on the exact byte sequence durably stored. It performs SHA-256 directly, without decoding, text normalization, newline conversion or stripping bytes. The version must retain its storage reference and this metadata:

```json
{"content_hash":{"algorithm":"sha256","basis":"raw_bytes"}}
```

`ck_document_versions_raw_hash_metadata` requires these values when extracted text is null. Missing metadata keys are rejected, including SQL NULL from JSON path lookup. Additional metadata may describe the media type, capture/extraction outcome and storage representation. Never hash a URL or storage URI, invent a digest, or use a placeholder to satisfy the required field. An actual empty byte sequence has a real SHA-256 digest and is different from content that has never been captured.

The database cannot prove that an external object exists or that a digest matches it. The agent/storage producer must save the bytes durably before returning a raw-only capture. Backend ingestion validates the reference/hash shape and records the hash basis; external byte verification awaits the storage integration. The existing `(document_id, content_hash)` uniqueness rule applies to both representations. Choosing an object-storage provider and verifying raw objects remain deployment prerequisites.

`content_hash` describes the version's original identity basis. It is not changed when another representation is added to that version. Raw bytes containing already-normalized UTF-8 text can have the same SHA-256 digest as that text; ingestion then reuses the version ID, original fetch timestamp and original raw reference. The original `raw_bytes` basis remains truthful even after `extracted_text` becomes available.

Ingestion maintains a separate backend-owned `metadata.representations` object describing the representations actually retained. `extracted_text` records `algorithm`, the computed normalized-text `sha256`, and `normalization: "nfc_lf_trim_v1"`. `raw` records the retained `storage_uri` and, when known, its `algorithm` and `sha256`. The existing `raw_sha256` field remains a compatibility alias for the retained raw digest. Adding raw storage to a text-based version preserves its text identity basis and records the raw digest independently.

Legacy metadata is enriched when its version is encountered, inside the same ingestion transaction. A legacy raw-based identity supplies its known raw digest; a legacy text capture with an undocumented raw digest keeps that digest unknown. No raw hash is inferred from a text-based identity. Other original producer metadata is retained, and missing original identity provenance is not invented. Agent-supplied `content_hash`, `raw_sha256` and `representations` fields cannot override these backend-owned facts. This uses the existing JSONB column and uniqueness constraint; no migration or bulk backfill is required.

## Deletion and lifecycle

Archive settings, memberships and archive-document links cascade when an otherwise deletable archive is removed. Other relationships use `RESTRICT`, including ownership, research history, versions, chunks, findings/evidence and job attempts. A deletion that would erase referenced provenance is rejected. Archive deletion with research history is therefore blocked; the existing `archived` status is the appropriate application operation until a deliberate retention/purge policy is designed.

Runs are logical sessions. Jobs are separately leased executable tasks and may optionally reference a run. The schema does not conflate a retry attempt, a job and a research run.

## Indexes and intended queries

| Index / key | Query or invariant |
| --- | --- |
| Email, publisher domain and canonical URL unique indexes | Identity lookup and global deduplication |
| Version `(document_id, content_hash)` | Reject repeated captured content for one document, using the documented hash basis |
| Chunk `(version_id, chunk_index)` and `(id, version_id)` | Ordered chunks and evidence/version integrity |
| Membership PK and partial owner uniqueness | Membership lookup and at most one owner row |
| Archive-document PK and document FK index | Archive contents and reverse document associations |
| `idx_document_versions_document_fetched` | A document's most recent fetched versions |
| `idx_research_runs_archive_created` | An archive's most recent research sessions |
| `idx_findings_first_observed` | Findings by observation time |
| `idx_chunks_fts` | `to_tsvector('simple', content)` GIN search without language-specific stemming |
| `idx_jobs_ready` | Pending work ordered by priority descending, creation ascending |
| `idx_jobs_run_after` | Pending work due to run |
| `idx_jobs_expired_leases` | Processing jobs whose lease expired |
| Job run FK index and idempotency uniqueness | Run work lookup and duplicate-request prevention |
| Attempt `(job_id, attempt_number)` | Unique retries and ordered attempt history |
| Other FK indexes | Parent/child traversal and referential checks |

The integration suite exercises concurrent priority claims with `FOR UPDATE SKIP LOCKED`, heartbeat renewal, bounded retries, concurrent expired-lease recovery, stale attempt rejection and transaction rollback on an identity/generation fence failure. Advisory-lock barriers also verify successful long ingestion across the original lease deadline and recovery/heartbeat contention during completion. The ORION-12 worker is disabled by default; recurring scheduling remains future work.

## URL normalization boundary

The document mapping normalizes scheme and host case, converts international hostnames to ASCII, removes default ports and fragments, and supplies `/` for an empty path. It preserves path case, trailing slashes, encoded path bytes, query order and tracking parameters. HTTP and HTTPS remain distinct. Malformed escapes, control/whitespace characters, backslashes, credentials and non-HTTP(S) URLs are rejected.

Fragment removal assumes the identity is the fetched HTTP resource; hash-routed application pages are not separate documents under this policy. Redirect targets, publisher canonical tags, query semantics and URL aliases require ingestion decisions. Similar-looking URLs are not otherwise merged. Publisher normalization trims surrounding whitespace and a terminal DNS dot and uses lowercase ASCII hostnames. Value converters apply these helpers on EF writes and query parameters; raw writers must follow the same canonicalization policy.

## Architecture review

| Question | Decision |
| --- | --- |
| Source of truth | PostgreSQL owns persisted identities, archive state, provenance and work history; processing metadata is derived as described above. |
| Ownership | Infrastructure is the schema/ORM owner; application operations own transactions. The Python service does not own this database model. |
| Dependencies | Domain has no framework dependencies. Infrastructure depends inward through Application to Domain; Api composes Infrastructure. |
| Boundaries | Scalar entity IDs and explicit foreign keys cross persistence boundaries. Service integration uses explicitly provisional versioned JSON, without shared ORM objects. |
| Failures | Database failures affect readiness/persistence, while liveness still succeeds. No implicit retries of multi-statement writes or startup migration is added. |
| Lifecycle | Scoped contexts own their connections/transactions. Tests dispose contexts, roll back data tests and delete only fixture-created databases. |
| Test seams | Real PostgreSQL through Testcontainers or an explicitly configured local server; API hosting uses WebApplicationFactory. No InMemory/SQLite substitute. |
| Compatibility | ORION-9 endpoints and configuration remain functional without a database. There is no previously shipped persistent schema to convert. |
| Observability | JSON logs, ProblemDetails trace IDs, separate process liveness and database connectivity readiness. No credentials in health responses. |
| Security | Runtime credentials come from configuration; migration permissions are separate deployment concerns. Archive and research HTTP endpoints enforce active internal users and persisted memberships. No caller identity headers or production fake agent are accepted. |

## Migrations and pending decisions

### ORION-12 execution design

| Architecture question | Decision |
| --- | --- |
| Source of truth | PostgreSQL owns runs, queue state, attempts and ingested provenance. Agent output is input to a backend transaction. |
| Ownership | Application authorizes submissions; the .NET worker owns queue transitions and persistence. Python owns research execution, without database credentials. |
| Dependencies | Domain remains framework-free; Application defines use cases/contracts; Infrastructure implements EF, HTTP and processing; Api composes them. |
| Boundaries | A provisional versioned JSON request/result uses source-local keys, never client-selected database identities. Public run IDs differ from internal job IDs. |
| Failures | Bounded HTTP calls and result sizes; finite sanitized error categories; transient backoff, permanent failures, lease recovery. No production fake client. |
| Lifecycle | Atomic run/job creation; short claims; no transaction during AI calls; fenced completion and ingestion in one transaction. Paused pending work waits; archived work cancels without deleting history. |
| Test seams | Existing test-only identity, isolated real PostgreSQL, replaceable agent client and independently callable processor/queue operations. |
| Compatibility | Keep the original seven migrations; append a forward migration for nonblank captures, run provenance on findings and one research-plan job per run. Existing findings retain nullable run provenance. Downgrades must not discard new provenance. |
| Observability | Public status exposes typed counts/retry timing and sanitized failures. Logs use run/job/attempt IDs and finite error codes, never agent bodies or credentials. |
| Security | Persisted archive roles gate submissions/status. Worker URLs and credentials come from configuration; redirects are disabled; result references resolve only within the submitted run's output. |

Submission locks the archive before checking lifecycle and the namespaced idempotency key. PostgreSQL uniqueness is the backstop. The fingerprint covers normalized client input, while the queue payload snapshots the authorized archive settings. Worker operations lock the job before the archive; archive HTTP operations do not lock existing jobs. Heartbeats run only during the external agent call. Before completion or failure handling, the processor cancels renewal and awaits its task, including any in-flight database call.

`OwnedAsync` validates job/run/archive IDs, processing status, worker identity and attempt generation, obtains the exclusive job-row lock, then checks lease expiry using fresh database wall-clock time. This post-lock check rejects a lease that expired while the SELECT waited on an unchanged locked row. Completion keeps that lock and the archive lock through ingestion and finalization. Once live ownership is acquired, the held row lock prevents recovery or reassignment; crossing the old deadline inside that transaction does not revoke ownership. The final update still checks IDs, processing status, worker and generation, but does not recheck elapsed lease time. Failure finalization uses the same rule. After rollback releases the lock, any new operation must acquire and validate ownership again. Heartbeats and recovery retain their expiry predicates.

No database transaction spans external HTTP work. Host cancellation and Npgsql command timeouts still bound database operations; output size/count limits bound ingestion work. Lock ordering stays job → archive → globally sorted publisher/document/version writes. A crash rolls back ingestion and releases its locks, allowing recovery of the expired processing lease. Atomic completion is also the replay boundary: an already terminal attempt cannot insert output again.

The new finding run FK is authoritative provenance, not a guessed backfill. Queue lease/status fields remain authoritative. Public statistics are derived from the committed output. Existing canonical URL, publisher, version-hash and archive-link uniqueness constraints protect global ingestion; source identities are upserted in deterministic order. No additional product table or broker is introduced.

The original seven migrations are unchanged. The seventh, `20261016095458_AllowRawOnlyDocumentVersions`, makes extracted text nullable and adds content-presence and raw-hash-metadata constraints. Existing document versions, hashes, metadata, chunks and evidence links are preserved; no data is rewritten or fabricated.

The eighth migration, `20261018073825_ImplementResearchExecution`, adds nullable finding/run provenance with RESTRICT, one research-plan job per run, and nonblank text/storage checks covering .NET Unicode whitespace. It validates existing rows without deleting or rewriting them; a legacy blank value stops the whole upgrade for explicit remediation. Downgrading refuses to drop populated finding/run provenance. Legacy findings keep null run IDs rather than receiving invented attribution.

The migration chain is the sole initialization path. Tests apply it from scratch, upgrade the original six-migration schema with existing content/evidence, upgrade from the first migration while preserving a user, execute idempotent SQL twice, compare catalog definitions and roll back/reapply on an empty disposable database. Empty reserved schemas and `citext` are retained by rollback rather than dropping shared namespaces/extensions. Downgrading the seventh migration takes a table lock and refuses to proceed while any raw-only version exists, instead of inventing extracted text or deleting captured versions.

After this chain is published, schema fixes should use new forward migrations. Down migrations drop product tables and data; they are intended for disposable development/test databases, not automatic production recovery. Any production rollback requires reviewed SQL and a verified backup/restore plan.
